A shared website for the NSF HDR community

The NSF Harnessing the Data Revolution (HDR) Ecosystem brings together five research institutes: A3D3, Imageomics, ID4, iHARP, and I-GUIDE. Its public website connects researchers, students, staff, and prospective participants with institute information, shared resources, publications, events, and machine learning challenges.

I worked on the platform through Ohio State’s Imageomics Institute. My role covered frontend development, content migration, feature implementation, and the fixes that follow a release. The work continued after the redesign: event dates change, challenge results need publishing, and links or mobile layouts need attention.

Why the site needed more than a visual update

The previous Google Sites content needed to move into a structure that could support a growing research community. Related information was spread across sections, navigation was difficult to scan, and visitors needed clearer routes to resources and programs.

The migration gave us a way to maintain the pages and their behavior together in GitHub. It also meant taking responsibility for details that a hosted page editor normally handles: responsive layouts, paths between directories, navigation behavior, and keeping changing content consistent. The repository already contained challenge material, so the redesign had to work alongside existing pages and preserve useful entry points.

I focused on making the designer’s direction work in HTML, CSS, and JavaScript, while carrying content into the new structure and incorporating stakeholder corrections. The challenge was keeping the information usable as the site changed, rather than treating publication as the end of the project.

My contribution and the team’s contribution

I implemented frontend pages, responsive styles, and interactive features, and submitted changes through GitHub. My commits include the initial page build, event search and filtering, news rendering, search improvements, and post-launch fixes. The redesign was integrated through the team’s review process.

The designer provided UX and visual direction. Research stakeholders supplied and reviewed content, while other contributors also changed the code and reviewed pull requests. Mobile updates, for example, went through review by another maintainer before being integrated.

I worked with shared components, but did not originate every part of that architecture. The initial modular header/footer loader came through a separate contribution. My later work included integrating behavior with asynchronously loaded navigation and correcting search initialization. That distinction matters: this was sustained work in a shared codebase.

What I implemented

Navigation across desktop, mobile, and nested pages

I built and refined the responsive frontend and navigation behavior, including the mobile menu. With institute and challenge pages at different directory depths, a link that worked from the homepage could still fail elsewhere. I worked on navigation links and initialization so menu and search handlers could attach after shared header content loaded.

Search that includes more than page titles

I improved the client-side search to resolve page URLs from the site root, index page text, and return results through the search interface. The current implementation discovers linked HTML pages, normalizes case, accents, and punctuation, and includes JavaScript-rendered event records. Those event records need explicit indexing because their content is not in the original HTML.

I also corrected search initialization so it could attach to the navigation after the shared header loaded.

Event filtering and pagination

I implemented event search alongside filters for event type and institute, then refined the listing to account for format and dates. Filtering changes the result set before pagination, and resets the current page so visitors do not land on an empty later page after narrowing their search.

I later adjusted events and news for mobile: six items per page instead of the desktop default of fifteen, with fewer visible page buttons. I refined this behavior after the initial implementation so the controls remained useful on smaller screens.

Dynamic content and challenge pages

I worked on data-driven news and events rendering and updated the homepage to select events from the available event data and challenge event content. This reduced the need to edit the homepage separately whenever the relevant events changed.

I also developed and refined challenge-page presentation, including date-based status behavior, winners content, and the Year 2 leaderboard view. Homepage event updates and the Year 2 leaderboard are examples of work beyond the original page migration. My contribution was the website implementation, not the underlying research or competition results.

Practical decisions and tradeoffs

Keeping the platform static

HTML, CSS, and browser-side JavaScript fit the GitHub-hosted platform without requiring a separate application server. The tradeoff is that content discovery, filtering, and state handling live in the frontend. Client-side search has to fetch and index pages, so index readiness and missing-page fallbacks matter. I worked within that architecture rather than introducing a new hosting stack.

Shared components and initialization

Central headers and footers make site-wide updates easier, but loading them asynchronously introduces timing and path issues. I contributed integration fixes and styling around that shared implementation. The component-loader history includes work from other contributors as well as mine.

Removing a control when it did not help

More controls were not always the right answer. A maintainer removed the extra challenge search/filter controls because their application was confusing and the main search was more useful. That was the maintainer’s change, not mine. It is a concrete example of the team refining the interface after seeing how the pieces fit together.

Tools & methods

HTML · CSS · JavaScript · Git & GitHub · Pull requests and code review · Content migration · Responsive layout debugging · Client-side search and data rendering

What changed

The platform now brings institute information, resources, publications, events, and challenge content into a shared site spanning more than 30 pages. Visitors can search across content and narrow event listings. Mobile pagination presents a shorter list, and homepage events can be selected from existing content instead of maintained as an unrelated block.

Those are implemented capabilities, not measured usability gains. I do not have validated before-and-after figures for task completion, traffic, search success, or time saved. The outcomes I can speak to directly are the features implemented, the content maintained, and the issues addressed after launch.

The work after the redesign

I continue to maintain content and frontend behavior as the research community’s needs change. HDR follow-up work includes mobile styling, image and alt-text corrections, challenge winners, and link repairs. For example, I repaired the Imageomics team link and later updated it to point to the Ohio State team page.

My Imageomics Institute website work is a related but separate project. It builds on shared ideas from the HDR platform. My work includes page and content development and corrections to news and events pagination.

My ongoing Imageomics work includes search improvements, event validation, publication pagination, and fixes to mobile navigation and carousel behavior. Some of that work is still in development, so I distinguish it from features already integrated into the site.

Lessons learned

Building a site includes keeping it useful

This work taught me to look past the page I was editing. A navigation change affects nested pages; a new event needs to appear in listings and search; a layout fix needs to survive a smaller screen. I’ve learned to make those relationships part of the implementation and review, and to treat maintenance as part of the product work.
